# Agent Note：以发现代替点名的搜索垫片

Status: implemented

[English](2026-10-22-search-shim-discovery.md) | 中文

## 问题

已部署的[网页搜索垫片](2026-09-21-deployed-web-search-shim.zh.md) 两次失效，两次的原因都出在清单上，而非网络。

第一，垫片从 `~/.dsh/settings.yaml` 解析路由。Harness 已弃用该文档：设置插件把它重命名为 `settings.yaml.imported`，并把实时值写入活动配置的 `cordis.patch.yml`。垫片继续读取那个不存在的文件，每个请求都报告 `no provider in agent-default-model`，于是落到无密钥引擎——可靠作答的网关从未被询问。它的解析器也读不了配置补丁文档（那是一串 loader 条目），所以仅把路径指向新文件也无济于事。

第二，无密钥层是三个引擎的固定顺序，由一组共享请求头解析。这些端点按 TLS 指纹拦截，以空页面回 `202`，或回 `429`；事件期间 DuckDuckGo HTML 与 Lite 都如此，Brave 全程回 `429`。作为唯一回退、却整体失效的一层，会让检索彻底消失。同期 Bing 把结果链接改为包在 `bing.com/ck/a?u=a1<base64url>` 中，解析器把它当作包装 URL 拒绝——同一代码路径里第二个独立的单点故障。

第三，早先手工运行遗留的垫片占着 24881 端口。单元每次重启都以 `EADDRINUSE` 失败，而单元没有声明启动限制，监督进程重试了 276 467 次。只要健康端点有应答，`doctor` 就把单元报告为健康，而应答的恰是那个遗留进程。

## 决定

检索是被发现的，不是被声明的。两层都不点名提供方，也不点名赢家。

**路由**从 Harness 实际写入的文档读取：活动配置的 `cordis.patch.yml`（loader 条目序列）、作为回退的已弃用 `settings.yaml`，以及 `.credentials.yaml`。YAML 读取器覆盖这些文档使用的块、序列与流式子集，包括旧文档写出的多行流式映射。声明了端点与凭据的路由会被询问其网关的原生搜索；其余都不能决定。以无引用作答的网关会在进程生命周期内被记住，因为那是能力事实，而瞬时失败会重试。

**引擎层**是 `server.mjs` 中的描述符清单，每条各自持有 URL、请求头、标记与可选的过渡页。`createEnginePool` 按近期成功排序，在连续两次失败后以最长 15 分钟的指数冷却隔离该引擎，并在全部冷却时仍逐个尝试。机器人检查（`202`、`403`、`429`、质询页面）与硬错误分开归类，使被限流的引擎被重试而不是被放弃。新增引擎就是一条描述符。

**重定向解包**是一个函数，而不是每个解析器各自过滤：DuckDuckGo 的 `uddg`、Bing 的 base64 `u=a1`、Google 的 `/url?q=`、Yahoo 的 `/RU=` 都解析为被引用的页面。无法读取的包装原样通过，于是解析器会把它作为包装拒绝，而不是当作结果返回。

**端口归属是有界的。** 垫片在致命监听失败时以状态 3 退出，在端口已由自身作答时以 0 退出；单元带有 `RestartPreventExitStatus=3`、60 秒内的 `StartLimitBurst=5` 与 `KillMode=mixed`；`doctor` 指出外部端口占用者，部署路径在重启单元前停止它。已是单元主进程的监听者绝不会被发送信号。

## 考虑过的替代方案

**保留提供方白名单并补上缺失的提供方。** 否决：故障本身就在于清单必须被编辑才能匹配现实。获得或失去服务端搜索的网关将需要改代码并重新部署。

**从 Harness API 而非其文档读取路由。** 否决：垫片是 systemd 下的独立进程，与运行中的 Harness 没有通道。读取它读取的同一批文档，是唯一按请求可得的信息源。

**为无密钥层驱动带 TLS 指纹仿真的真实浏览器**，即 [duckduckgo-mcp-server](https://github.com/nickclyde/duckduckgo-mcp-server) 用 `curl_cffi` 所做的方式。目前否决：这会给零依赖的 Node 工具引入 Python 或原生依赖，而同样的可靠性可以通过多引擎与"哪个引擎答过"的记忆达到。引擎描述符接缝正是将来加入这类后端而无需改动流水线的位置。

**让单元永远重试。** 否决：276 467 次重启循环正是掩盖遗留进程的原因。有界的启动限制让失效的部署可见，而不是吵闹。

**保护机制而非文件名。** 同步原本已按标记拒绝丢失垫片，但针对入口点名称的标记会被它所替换的有缺陷版本满足。标记现在点名引擎池、网关能力记忆、监听失败分类、配置补丁路由来源与单元的启动限制，因此恢复旧版垫片会令同步失败。

## 后果

网关未实现搜索的路由每个进程只浪费一个请求，而不是每次搜索浪费一个，之后由引擎作答。引擎顺序按网络实际允许的情况自适应，无需重新部署，因此对本主机拦截的引擎会停止被优先尝试。两层都记录结果，`GET /engines` 暴露池的失败、机器人检查、成功与冷却，因此日志会指出实际作答的检索。

引擎清单仍然是标记知识的清单：改变页面的引擎需要更新其描述符。这比先前的整层是更小的单元，且在此期间其他引擎继续作答。垫片依赖网关的 OpenAI 兼容 `web` 插件契约与各引擎的标记，两者都不稳定；层级边界正是让任一处故障成为被记录的一次未命中而非错误的原因。

`tools/dsh-search-shim/tests/` 下的测试用注入的传输与时钟覆盖流水线，因此引擎变更会在部署看到之前先对着录制的标记得到验证。
